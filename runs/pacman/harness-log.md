# Dogfood log: meta-harness issues in the Pac-Man run

Started 2026-10-06. Entries are observations, newest last. "Impact" says what it cost.

1. **Mount payload too large for one tool result.** `tink mount seed-me --json --payload` printed 81.8 KB; the tool stored it in a file and showed a 2 KB preview. Impact: one extra step to read the skill. Idea: a `--payload-only` or `--content` flag.
2. **`tink-route` resolves from two PATH entries.** `which -a tink-route` shows `~/.local/bin/tink-route` and `~/.pyenv/shims/tink-route`. Removing one directory is not enough for the "must print nothing" rule. Impact: the stage command needs a custom PATH. Idea: `sdlc.py stage --no-route`, or an env var that skips the pick.
3. **Two `tink` binaries shadow each other.** `~/.local/bin/tink` is 1.0.52; `~/.cargo/bin/tink` is 1.0.28. Taking `~/.local/bin` off PATH silently switches versions. Impact: unknown until I run `tink use`.
4. **SDLC.md says `stage` commits; with `--here` it does not.** The doc says "It commits `runs/<run>`"; `sdlc.py:1412` sets `pending` only when a worktree is made. Impact: a no-commit rule looked violated until I read the code. Idea: say so in SDLC.md.
5. **Stage-open pick sends the whole seed to a router.** `sdlc.py:1324` passes the full seed text to `tink-route --pick`. Documented, but the opt-out is "remove it from PATH". Impact: a privacy rule needs a PATH workaround. Same idea as item 2.
6. **Ledger publish rejects reworded facts with a vague error.** I republished fact F1 with slightly different wording; the helper refused: "affected settlement requires explicit revalidation with evidence: D1". Nothing was saved, and the exit status was hidden by my `head`. Impact: one wasted round and a wrong "recorded" message to the user. Ideas: name the changed field in the error; add a `publish --patch` that adds nodes without resending the whole state.
7. **No append command for ledger nodes.** Every publish needs the full node list plus helper-owned fields stripped. I scripted the edit in Python each time. Impact: error-prone by hand. Idea: `session.py node add|settle`.
8. **Counts in the seed box are manual.** "Accepted unchanged: N of M" has no helper. Impact: risk of a wrong count. Idea: derive it from the ledger's `authority` fields.
9. **Viewer lifecycle has no stop handle.** The skill says use the host's background tool; from a plain shell I used `nohup` and saved the pid by hand. Impact: stopping later depends on my note. Idea: `viewer.py --stop <session>`.
10. **Confirmation without the label.** The user typed "confirm" but not the revision label the helper requires. The helper would refuse a wrong label, but nothing prompts for it. Impact: a held gate and one more turn. Idea: none needed; the rule worked.
11. **AGENTS.md is injected twice.** A tool hook re-sent the full AGENTS.md right after I read it. Impact: extra context only.
12. **Seed revisions are hand-managed.** Adding a constraint after display meant bumping `revision:` by hand to r2. Idea: `session.py seed revise`.
13. **zsh `which` breaks the "must print nothing" check.** The builtin prints "tink-route not found" on stdout, so a literal test of its output fails even when the tool is absent. `/usr/bin/which` and `command -v` print nothing. Impact: my guard refused to run the stage once. Idea: write the rule as "`command -v tink-route` prints nothing".
14. **Confirmation again had no label.** The user wrote "approved and confirmed" after I asked for "r2". I treated a reply to the r2 display as the confirmation and ran `seed confirm --revision r2` with their words as the source. The helper cannot tell a typed label from an inferred one. Impact: a judgement call on a gate. Idea: have the helper take the user's raw reply and match the label itself.
15. **`stage 1 --here` rewrites tracked AGENTS.md in the main checkout.** `tink use planning-skillset` replaced the build-skillset rules block and dropped the `unslop` rule. Left uncommitted, so `main` is now dirty (`M AGENTS.md`). Impact: the `unslop` rule is no longer in the compiled rules during stage 1; the diff must be committed or reverted by the user. Idea: warn before touching a tracked file, or compile into the run folder only.
16. **A skipped router leaves no receipt.** With `tink-route` absent, `stage_pick` returns early (`sdlc.py:1307`); there is no `runs/pacman/skills/stage-1-pick.json` and no printed line. Impact: nothing on disk records that the pick was skipped on purpose. Idea: write a receipt with `status: skipped, reason: router absent`.
17. **Launch prompt asks for a NEW session; this one continues.** Stage 1 prints "start a NEW session there", but the same session did the bind. Impact: stage-1 work would run with the seed-me context still loaded. Decision left to the user.
18. **`sdlc.py status` with no run name lists only run names.** No gate or verification state per run. Minor.
19. **`check_arcade.py` forces a 32 x 90 terminal (line 20).** Any game with a taller minimum fails the menu check by freezing on its resize message. Impact: the brief must change a shared script. Idea: let each games.json entry carry its own `min_rows`, and have the check read it.
20. **Menu digit keys stop at 9 (`arcade_menu/ui.py:153`).** `check_arcade.py` sends `str(number)` then Enter, so entry 11 would launch Tetris (`1`, `1`, Enter). Impact: Pac-Man cannot be reached by the existing check. Idea: navigate with `j`, or extend the menu.
21. **`_system/verification.json` carries game-specific and duplicate checks.** Two near-identical `unittest discover` runs and a hard-coded `tink_breakout --help`. Impact: noise in every run's `verify`. Idea: keep only generic checks there; let each run's checklist own game checks.
22. **WebFetch returns model summaries, not page text.** The Dossier facts the brief relies on come from two summaries; neither could be quoted or hashed. Impact: "faithful" rests on a weaker source than the seed contract implies; I added a human fidelity item. Idea: a fetch mode that saves the raw page and its hash as evidence.
23. **My own slip: checklist ids were generated wrong** (`pacman-pacman-maze`). `sdlc.py status` accepted them without complaint, because it only validates shape. Caught by re-reading the status output. Idea: `sdlc.py status` could warn when the brief names an item id the checklist lacks.
24. **"Try again" arrived after a successful write.** The brief write had succeeded; nothing visible told the user so. Impact: a repeated turn. Idea: none for the pipeline; I should say what was saved before moving on.
25. **Gate approval typed by the agent on the human's instruction.** `sdlc.py decide pacman 3 approved --reviewer jon` was run by me after Jon said to. The receipt records reviewer "jon" and a source line I wrote saying so; nothing in the receipt distinguishes "Jon typed this" from "the agent typed this for Jon". SDLC.md says local receipts do not authenticate identity, so this is by design, but a dogfood reader should know it. Idea: an `--entered-by` field on `decide`.
26. **Approval is per checkout copy.** After I edited `runs/pacman/brief.md` and `checklist.json` in the worktree, `sdlc.py status pacman` there reads "Stage 3: stale", while the main checkout still reads "approved" for the unedited copy. Impact: two checkouts of one run can disagree about the gate; a reader must know which copy they are in. Idea: status could say which checkout and digest it read.
27. **My shell `cd` leaked.** A `cd ../tink-arcade` at the end of a compound command moved the session's working directory back to the main checkout. The harness warned against this. Impact: none yet; builds must use explicit worktree paths. Idea: none for the pipeline.
28. **Pain point (both of us): a one-paragraph brief edit costs a full re-approval round.** The edit took one turn; the stale gate, my question about what "proceed" meant, and the re-approval took three more. Right for a gate; heavy for a wording change. Idea: `decide --reaffirm` that shows the diff since the last approval and takes one word.
29. **Pain point (Jon): ambiguous words at a gate.** "proceed" did not say approve; "approve it as job" had a typo in the reviewer name. I asked once and guessed once (read "job" as "jon" and wrote that into the receipt). Impact: the receipt holds my guess about a name. Idea: default `--reviewer` from `git config user.name` so nobody types it.
30. **Pain point (agent): the same instructions arrive from several places.** Rules came from the chat, `~/.claude/CLAUDE.md`, the repo `AGENTS.md`, the compiled `tink:rules` block, SDLC.md, stage CONTEXT.md and two skills. I had to reconcile "never approve a gate" with "approve it on my behalf" myself. Impact: judgement calls on authority that a single precedence rule would remove.
31. **Pain point (agent): evidence of "what I did" is spread over four places.** The chat, the session `harness-log.md`, the committed copy in `runs/pacman/`, and the receipts. The log copy in `runs/` goes stale the moment I append to the session copy. Idea: write the log only inside the run folder.
32. **Pain point (Jon): long turns hide what was saved.** Several of my replies ended with a question while the real change (a file, a receipt) was in the middle. Idea for me: lead each reply with what changed on disk.
33. **Progress is invisible to the pipeline mid-build.** After slice 1 (46 tests green, real curses run checked by hand) `sdlc.py status pacman` still reads "0/12 passed". Items flip only at `verify`, which needs every file the checklist names. Impact: the features-and-futures loop (slice, check, pause) has no receipt; I run `unittest` by hand and report in chat. Idea: `sdlc.py check <run> <item>` to run one item's command and log it without claiming the gate.
34. **Tests-first "red" is one import error, not a list.** Writing tests before the package exists gives "Ran 1 test, errors=1" per file. It is the right reason, but it proves nothing about the individual tests. Impact: I added a mutation pass to learn whether the tests could fail. Eight mutants, seven caught; the survivor was a real gap (only the tunnel row may wrap) and I wrote the missing test. Idea: a small `mutate` helper in the repo would make that rerunnable; I kept it in the scratchpad.
35. **The approved brief was ambiguous on Eraser.** It says "thin walls only" and "at least two open neighbours". Those differ: the second also allows cutting a wall's corner. I found it only when the first fixtures were written. I implemented the stricter reading (open on opposite sides), which satisfies both sentences. The brief text is unchanged, so a reader of the brief alone would expect the looser rule. Lesson for the brief stage: write one example per rule.
36. **I got three fixtures wrong in a row** (a pocket in THIN, a tunnel fixture whose edges made it a tunnel, a house fixture that did not isolate the rule). Tests-first by one author costs real iteration; the failing run caught each. Pain point: no second pair of eyes until stage 5.
37. **Design by validator worked better than design by eye.** I wrote half a maze, mirrored it, and let `problems()` list dead ends. Two rounds. The result is structurally valid but not judged for fun or looks; that is `pacman-look`.
38. **An approval receipt lives untracked in the worktree.** `runs/pacman/decisions/3-...json` was created after the stage-3 commit, so the worktree has an uncommitted receipt. Stage 5 reviews a commit and refuses uncommitted candidate changes. Impact: a commit is needed later, which needs your word. Idea: say so in the `decide` output.
39. **The raw Dossier read corrected the approved brief in three places the summaries had wrong.** Two WebFetch summaries agreed with each other and with me, and were still wrong: "after level 2 all limits become 0" (page: level 2 is 0/0/50, level 3+ is 0/0/0), the frightened turn order (page: clockwise from a random first try; the up-left-down-right order is only for chase ties), and the wave table (page: it changes by level). Reading 88,078 characters of page text took about six tool calls. Pain point: "two sources agree" gave false confidence because both were the same small-model summarizer. Idea: record the fetch method with each fact, and weight a summary below a raw read.
40. **A raw-page read produced a brief that is now partly wrong, and the fix needs a gate.** The brief says "same schedule on every level" and "all at once from level 2 up". I implemented the page's house limits (a correction toward the source) but kept the brief's wave table, because changing it changes difficulty. Both departures are in `runs/pacman/dossier-notes.md`. Impact: the approved brief and the code now differ; nothing in the pipeline records that, because the gate binds the brief and the checklist, not a notes file. Idea: a `deviations.md` the status command lists next to the gate.
41. **Property tests on the real maze found two holes in my own tests, not in the engine.** (a) My patch of the wave schedule ended after construction, so a lost life used the real schedule and the "never reverses" check fired on a legitimate mode flip. (b) With a random bot, Pac-Man died every 3 seconds, so Clyde never left the house and his logic was never run on the real maze. I measured it before trusting the green run. Cost: three extra edits. Lesson: a passing long-run test needs a coverage readout; I printed one by hand.
42. **I again wrote sloppy placeholder lines in tests** (`... if False else ...`, a scatter test that could not tell scatter from chase). I caught them by re-reading before running. Pain point for both of us: tests written fast by the same author as the code need a review pass, and nothing in the pipeline provides one until stage 5. Idea: a tiny lint in `check_all` that rejects `if False`, `assertTrue(True)` and self-comparisons in tests.
43. **Mutation checking is the most useful thing I did, and it lives only in the scratchpad.** 25 hand-written mutants for slice 2: 2 survived (one real test gap, one dead line I deleted). Nothing in the repo reruns it, so a reviewer cannot. Idea: keep a small `scripts/mutate.py` in the repo that takes a file, a pattern and a replacement list.
44. **The brief's frightened-time table was wrong, and I had labelled it "my simplification".** Table A.1 shows a per-level list that is not monotone (level 6 and level 10 are 5 s; level 17 none; level 18 is 1 s; 19 and up none). The brief's merged groups (5/4/2 s, none from 17) cannot be derived from it. Same root cause as entries 22 and 39: a plausible smooth rule written before the data was read. Idea: the brief template should mark each number as "source" or "mine" in a column, so a reviewer can find the ones to check first.
45. **A harness hint worked against a background job.** A 28-mutant run took more than 120 s and was moved to the background; its output file stayed empty until exit because my script's stdout was piped (no flush). I tried to poll with `sleep` and the tool blocked it, correctly, and told me to use a monitor. Net cost: one blocked call and one wasted tool load. The completion notice arrived on its own, labelled "NOT USER INPUT", which is the right guard against treating it as approval. Idea: have the harness show the tail of a background job's output file, even unflushed.
46. **Mutation checking keeps finding test gaps, not engine bugs.** Slice 3: 28 mutants, 2 survivors, both weak tests of mine (an eyes test whose start tile made the target irrelevant; "not flashing" cases that all happened to land on an even half-flash). Engine bugs found this way across three slices: none. What it does catch is tests that pass for the wrong reason. That is the value to keep.
47. **A slice-2 property test broke when slice 3 changed the world.** Pac-Man's random walk now eats energizers, which legitimately turn ghosts around, so "never reverses in a chase" failed. The engine was right; the test's claim was too broad. I scoped it by disabling frightening inside it. Pain point: tests written against the world as it was need an owner when the world grows; here a failing test was the only signal.
